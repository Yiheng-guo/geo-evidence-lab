# 产品定位、改动与需求场景

## 原包与本项目的关系

原包是以豆包为中心的 GEO 工作流整合包，含总控、关键词、文章写作、平台改写和研究五个 Skill，以及 Python 脚本、表格和操作资料。本项目在阅读业务思路后重新编写，未收录授权不明确的原文件。

上一个 v0.1 交付侧重“内容任务与效果验证”，没有完整移植原包五个模块。不能称为原包的完整功能升级，也不能称为全自动 GEO 系统。

| 环节 | 原包 | v0.1 新实现 | v0.2 补充 |
| --- | --- | --- | --- |
| 资料准备 | 客户档案与表格 | 手工填写 JSON | init 建项目，默认忽略客户数据 |
| 问题 / 关键词 | 规则生成关键词 | 用户提供问题，冻结标准 | Skill 补充问题研究方法；CLI 仍不挖搜索量 |
| 内容生产 | 写稿提示和平台规则 | 生成通用 brief | 支持单题 brief，补来源核查、成稿与平台适配规范 |
| 采集 | 豆包半自动操作指导 | 手工提供 JSON | CSV 采集表与导入，pending 和 unavailable 分开 |
| 发布前诊断 | 豆包诊断报告 | 只有前后对比 | 独立 baseline 报告，无后测也能诊断现状 |
| 效果检测 | 汇总导入的记录 | 固定条件配对、提及与自有引用分开 | 按引擎／模式／上下文拆分；人工推荐标注与独立分母 |
| 报告 | 结构化 Markdown | HTML 与 JSON，保留原始回答 | 排除记录展开、人工判断依据、基线与对比统一界面 |
| 计划冻结 | 项目变量驱动 | 冻结整个档案 | 只冻结检测字段，补充证据不要求重做基线；仍兼容旧计划 |

冻结和分母处理是在提高比较质量，不是证明因果效果。

## 场景一：内容负责人不知道先写什么

品牌做团队协作工具，客户经常问导出、权限和迁移。负责人希望内容资源投入到真实决策问题，而不是只写品牌介绍。

输入：产品事实、目标读者、客户问题、待核验来源。动作：建项目、固定问题、采集基线，针对一个问题生成 brief；Agent 核验来源后写文章。产物：现状、证据缺口、文章与主张—来源表。

价值：能把内容任务与用户问题关联。前提：有人提供真实问题、核查事实并完成写作。这里是功能场景示例，不是真实客户案例。

## 场景二：顾问需要向客户解释工作成果

客户问“发布了内容，AI 搜索到底有什么变化”。顾问需要拿出原始回答，而非截一个有利结果。

输入：一致问题和采集条件下的前后记录、发布时间与 URL。动作：导入采集表，配对比较，展开证据，人工标注推荐语境。产物：可追踪的描述性变化与缺口。

价值：减少换题、漏数据和把提及当推荐的问题。限制：不能仅凭该报告向客户承诺由发稿导致的效果或收入。

## 场景三：产品经理评估新的内容渠道

产品经理想比较不同 AI 引擎对品牌的可见性，决定是否继续做内容实验。

输入：同一问题库在多个引擎、相近条件下的采集记录。动作：分别生成采集表，导入后合并 JSON 数组，再比较分组。产物：引擎／模式／上下文各组的前后变化与原始证据。

价值：避免总体数据掩盖引擎差异。限制：每组样本量与问题构成仍需检查；投入回报还需要单独记录人力、内容费用与转化。

## 不适合的诉求

“保证豆包推荐我”“自动刷出排名”“一键发到所有平台”“证明收入增长都是 GEO 造成的”均不是本项目可兑现的能力。目标场景来自产品设计推断，尚待真实用户使用与访谈验证。
